# AI Agent Operating Model

## Purpose

This page defines how AI agents should work inside the Onelink workspace so that edits remain structurally correct for both the human team and the repository layout.

Use this page when:

- an AI agent is making code or docs changes
- a human analyst needs to understand how the agent should reason about the repo
- a task spans code, docs, deployment, or multiple repos

## Working Assumptions

An agent working in Onelink should assume:

- code is the primary source of truth for what exists today
- docs are required to explain current architecture, operating rules, and target direction
- target-direction pages do not prove that a runtime feature already exists
- `enterprise/` is an active technical layer and must be checked before editing shared logic
- `docs/` is a separate Git repository mounted inside the app repo

## Repository Boundaries

The agent works across these boundaries:

- `onelink`
  - application code repository
- `onelink/docs`
  - docs repository mounted as submodule
- `onelink/.codex/skills`
  - versioned project skill source
- `$CODEX_HOME/skills`
  - installed local skill library

Rule:

- edit code in `onelink`
- edit docs content in `onelink/docs`
- edit versioned skill definitions in `onelink/.codex/skills`
- sync installed runtime skills in `$CODEX_HOME/skills`

Do not blur these commit boundaries.

## Read Order

Before changing a feature, the agent should normally read in this order:

1. the concrete code paths in `app/`, `enterprise/`, `config/`, `db/`, `spec/`, and `swagger/`
2. [Current Architecture](/platform/current-architecture)
3. [Repository Map](/platform/repository-map)
4. the surface-specific execution guide
5. the matching specialized skill

If the task is docs-specific, also read:

- [Docs Repository Workflow](/contributing-guide/docs-repository-workflow)
- `docs/AGENTS.md`

## Task Classification

The agent should classify each task before editing:

- backend
- frontend
- api
- integrations
- captain/ai
- docs
- deployment
- gitops/upstream
- mixed

If a task is mixed, the agent should still keep repo-specific commits separate.

## Commit Discipline

### App Code

When files outside `docs/` change:

- commit in `onelink`

### Docs Content

When files under `docs/` change:

- commit in `onelink/docs` first
- then update the submodule pointer in `onelink` if needed

### Skills

When local skills change:

- update the versioned files in `onelink/.codex/skills`
- sync the installed copy with `./.codex/scripts/sync-skills.sh to-codex-home`
- commit the versioned project copy in `onelink`

## Staging Discipline

The agent should avoid mixing unrelated work in one commit.

Rules:

- do not commit unrelated staged files just because they are already staged
- use path-limited commits when the repo already has other local work in progress
- if a task touches app code and docs, create separate commits in the correct repos

## Verification Discipline

Verification should match the touched surface:

- backend:
  - narrow request/model/service specs
- frontend:
  - narrow Vitest, Histoire, or manual dashboard smoke check
- api:
  - request specs plus Swagger build
- docs:
  - validate `docs.json`, navigation references, and OpenAPI sync where relevant
- deployment:
  - syntax and config checks appropriate to the touched files

Do not claim verification that was not run.

### Prepared October 10 runtime verification

The isolated hotfix gate must cover provider receipt success without immediate readback, retained occupancy after local cancellation, operation-specific confirmations, structured scheduling errors, independent incoming-message fences and a two-connection row-lock race for obsolete handoffs. Delayed create-receipt verification is read-only, bounded to six attempts and uses the existing reconciliation job; it must not replay creation or downgrade the acknowledged operation.

Synthetic playground verification uses temporary session JSON, shared scheduling validation and native tool schemas. Real writes require reads plus approval of the exact tool, target, payload and record snapshot. Verify revocation and reset races at the final provider write gate, not only the UI toggle. Unsupported transports return an explicit denial. Native Ruby checks require isolated PostgreSQL, pgvector and Redis; component tests alone do not verify these boundaries. Do not use customer databases, send customer messages or invoke live provider mutations for the gate.

### Prepared October 11 custom guardrail boundaries

The prepared implementation stores per-agent checks in `config.safety_settings.custom_rules`. Read `enterprise/lib/captain/safety/custom_rules_config.rb` and the services under `enterprise/app/services/captain/safety/` before changing this behavior. The profile supports at most 20 rules, with a stable ID, name, direction, condition, action, enabled flag and optional static message. Within the current `input` or `output` direction, enabled conditions keep their saved order and the checker selects the first matching ID. The server resolves the action from the saved rule. No enabled rules for that direction means no custom-check model request.

Preserve these runtime boundaries:

- `CustomRulesRuntime.check_input!` runs before the main agent starts work and again for a routed destination before it continues. A matched stop or unavailable check prevents that agent's main work.
- `AgentRunnerService` checks the final public text using the responding agent's profile. This includes deterministic summaries of completed tools and public exception fallbacks, even when the response also contains `error_class`.
- An output `rewrite` gets at most one text-only repair. Recheck the replacement against all enabled output rules and `Llm::SafetyPolicy` before returning it. The repair has no tools; it cannot rerun tools, perform an action or add an unverified execution claim.
- A block, handoff match, failed check, failed repair or rejected replacement stops the automatic reply. `ResponseBuilderJob` uses the system handoff path and rechecks the existing conversation, message, control and actor fence under the persistence lock. A stale run sends neither a handoff message nor a handoff.
- The optional public handoff text comes from the currently saved, enabled rule with the matching ID and direction on the responding agent. Ignore payload-supplied message text. Check the saved text for sensitive information before sending it, and send it once with the fenced handoff. This path works when the ordinary human-handoff tool or its message is disabled.
- Strip `custom_guardrail` and authorization markers from ordinary model output. Only server-generated stop envelopes carry those fields into the handoff path.

Custom checks accept text candidates of at most 10,000 characters. Invalid candidate types and longer strings are rejected before inference; they do not silently truncate a check. The rewrite engine also rejects invalid or oversized text. The last customer-message excerpt used for output checks is bounded to 2,000 characters and remains untrusted context. Text checks do not establish image, audio or medical validation.

`CAPTAIN_CUSTOM_GUARDRAIL_MODEL` is a separate installation setting with the current default `openai/gpt-6-luna`. The selected model must support the structured rule-ID response. The native Microsoft Decision 1 adapter is limited to asynchronous handoff/completion reason classification; it does not replace custom guardrails. Provider moderation uses its separate `CAPTAIN_MODERATION_MODEL` and existing policy; its unavailable-provider default remains `fail_open`. Custom-check failures stop the automatic reply independently of that moderation setting.

Verification must cover input stops, destination and response actors, forged metadata, final and fallback output checks, the single repair and its recheck, saved static text, disabled or deleted rules, secret-shaped text and stale handoff races. Benchmark scores do not establish that these runtime boundaries were tested. Record the exact local and server checks actually run; this section does not assert completed verification or deployment.

## Handoff Rule

At the end of a task, the agent should leave the project in a state where a human can answer these questions quickly:

- what changed
- in which repo it changed
- what was verified
- what remains uncommitted locally
- whether the parent repo still needs a docs submodule pointer update
