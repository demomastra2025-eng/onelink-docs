# DEV UI Full Regression Test Plan

Status: current operational plan for full UI confidence testing on `https://dev.one-link.kz`.

Primary goal: after execution, the team should know which OneLink UI surfaces are production-ready, which are blocked by data/config/provider state, and which defects must be fixed before release.

This plan is intentionally internal. It references runtime paths, test users, logs, DB reads, and Hermes skills.

## Coverage Reality

A full OneLink regression run is designed for **release confidence**, not a mathematical guarantee that every possible positive and negative scenario has been exhausted. The practical target is to cover each important flow at the deepest evidence layer that is safe and available on DEV.

Use this ladder for every test row:

1. `UI`: the browser-visible flow works or fails with clear evidence.
2. `API`: the frontend request/response contract is verified, including expected 2xx/4xx/422 behavior.
3. `DB`: the expected DEV database state was created, updated, deleted, or intentionally unchanged.
4. `JOB/QUEUE`: background jobs, retries, or scheduled work are observed when the feature depends on them.
5. `PROVIDER/LIVE`: an external provider, QR session, webhook callback, telephony call, delivery receipt, or sidecar completed the real integration path.
6. `AUTOMATED`: targeted RSpec/Vitest/lint/build checks exist or were run for the code slice.

Do not collapse these into one vague `PASS`. A module can be `UI+API+DB PASS` while still `PROVIDER/LIVE NOT RUN`.

## Hermes And Project Test Capability

Current tooling available to Hermes on this project:

- Browser tools for live DEV UI navigation, screenshots, console capture, and manual E2E-style interaction.
- Rails runner/DB read probes for `chatwoot_dev` state checks.
- Rails logs/systemd/service probes for DEV runtime correlation.
- RSpec for backend models, services, jobs, requests, controllers, policies, Captain, integrations, and runtime contracts.
- Vitest for frontend stores, components, composables, routes, helpers, and API clients.
- ESLint/RuboCop/syntax checks for static verification.
- Sidecar/provider probes where local services expose health/status endpoints.

Current important gaps:

- The app repo has broad RSpec/Vitest coverage, but no committed Playwright/Cypress-style browser E2E suite was identified in the current package dependencies. Hermes browser QA is therefore the live browser layer unless/until a formal E2E suite is added.
- External providers cannot be exhaustively covered without dedicated sandbox credentials, test phone/accounts, callback fixtures, and safe rate-limit budgets.
- QR, WhatsApp/Weixin delivery, Fonoster/audio, Postiz/Kaspi/provider payment/media flows require live/sandbox proof before `PROVIDER/LIVE PASS`.
- PROD proof is out of scope without explicit approval.

## Safety Rules

1. Test DEV only unless explicit production approval is given.
2. Report `PROD touched: no` in every test report unless production was explicitly approved.
3. Never print or store passwords, session cookies, auth tokens, QR tickets, provider secrets, or `.env` values.
4. Use DEV-safe test entity names with a run prefix, for example `QA-UI-YYYYMMDD-HHMM-<module>`.
5. Record every created/changed DEV entity in the run log.
6. Do not call a module `PASS` if there are unresolved console errors or failed API requests affecting that module.
7. Do not call a visual/browser flow `PASS` from curl or code checks alone.

## Evidence Standard

Every tested area must record:

- Test ID.
- URL.
- User/account/role when relevant.
- Preconditions and test data.
- Steps executed.
- Expected result.
- Actual result.
- Browser console after clearing old logs.
- Failed API/network requests.
- Screenshot path when visual evidence matters.
- Backend/log/DB evidence when server state matters.
- Created/changed DEV entities.
- Evidence layers covered: `UI`, `API`, `DB`, `JOB/QUEUE`, `PROVIDER/LIVE`, `AUTOMATED`.
- Result: `PASS`, `PARTIAL PASS`, `BUG`, `BLOCKED`, `NOT RUN`, or `N/A`.

Browser procedure:

1. Open the target route.
2. Immediately clear browser console noise.
3. Execute the test steps.
4. Capture snapshot or screenshot if relevant.
5. Read console and network/API failures after the action.
6. If server state is involved, correlate with logs/DB/API reads.

Known non-blocking DEV noise:

- Browser extension errors such as `Could not establish connection. Receiving end does not exist` are not app bugs unless correlated with app behavior.
- Lit/Vite dev-mode warnings are expected in DEV unless the task is production build hardening.

## Result Definitions

- `PASS`: all required evidence layers for that test row are satisfied. For normal CRUD this usually means at least `UI+API+DB`; for integration rows it may also require `JOB/QUEUE` or `PROVIDER/LIVE`.
- `PARTIAL PASS`: some layers passed, but at least one material layer is intentionally not run or unavailable. Example: `UI+API+DB PASS; PROVIDER/LIVE NOT RUN`.
- `BUG`: reproducible defect with steps/evidence.
- `BLOCKED`: cannot test due to missing credentials, unavailable provider, missing feature flag, missing data, service outage, or permission boundary.
- `NOT RUN`: intentionally deferred or outside this run.
- `N/A`: not applicable for the current account/feature set.

Release confidence labels:

- `UI PASS`: browser-visible behavior passed, but backend/live depth may still be absent.
- `UI+API+DB PASS`: browser behavior and server persistence/contract passed for DEV.
- `LIVE PASS`: external provider/sidecar/callback/delivery path completed with evidence.
- `DEV UI PASS`: full target surface verified on DEV at the depth required by the test rows.
- `CODE-SLICE DONE`: code/spec checks passed, but live DEV UI was not verified.
- `PROD PASS`: only after approved production deployment and live production proof.

## Severity Model

- `Critical`: blocks login, primary routing, conversation handling, message sending, data integrity, or causes cross-account/security exposure.
- `High`: breaks an important customer/admin flow with no reasonable workaround.
- `Medium`: broken feature or confusing behavior with workaround available.
- `Low`: visual/content/minor UX issue that does not block task completion.

Priority model:

- `P0`: fix before any release/demo.
- `P1`: fix before customer-facing release.
- `P2`: fix soon; acceptable with known workaround.
- `P3`: backlog polish.

## Execution Phases

### Phase 0: Setup

1. Generate run id: `QA-UI-YYYYMMDD-HHMM`.
2. Create evidence directory: `/root/crafty/onelink/qa-runs/<run-id>/`.
3. Create subdirectories:
   - `screenshots/`
   - `console/`
   - `api/`
   - `logs/`
4. Run entry checks.
5. Confirm account id and user role.
6. Open browser and clear console.

### Phase 1: Route Smoke

Goal: prove all major route families open or intentionally guard/redirect.

Run all matrix rows that only require navigation and read-only inspection.

Output: route smoke result list with console/API failures.

### Phase 2: Critical User Flows

Goal: prove the primary operating flows work end-to-end on DEV.

Minimum critical flows:

1. Login and dashboard landing.
2. Conversation list and detail.
3. Message composer usability without necessarily sending external provider traffic.
4. Inbox/channel setup list and new-channel dialog.
5. One QR/auth-artifact flow if DEV test provider state exists.
6. Captain assistant list/detail/tools/documents.
7. CRM contact/company/deal navigation.
8. Settings/admin core pages.
9. Search and notifications.

Output: critical-flow report with screenshots and bugs.

### Phase 3: Module Regression

Goal: cover the rest of the product surfaces.

Execute the remaining matrix by module:

1. Settings/admin.
2. Automations/macros/integrations/webhooks.
3. Scheduling.
4. SMM/content.
5. Help Center.
6. Campaigns/outbound.
7. Voice/calls when live DEV dependencies are available.

Output: module-by-module status.

### Phase 4: Runtime Correlation

Goal: prevent false UI conclusions.

Use runtime evidence for:

- QR/auth artifacts.
- Captain tools/evals/knowledge/observability.
- Channel/provider state.
- Voice/calls.
- 500 errors or unexpected 404s.
- Repeated failed API requests.

Minimum logs/probes:

- Rails service active.
- Rails logs around error timestamp.
- DB read for entity existence when route depends on `account_id`, `inbox_id`, `assistant_id`, etc.
- Sidekiq/provider/sidecar logs only when relevant.

### Phase 5: Triage And Retest

1. Deduplicate issues.
2. Assign severity and owner.
3. Mark release blockers.
4. Fixes are not part of this plan unless explicitly requested.
5. After fixes, rerun only impacted test IDs plus any adjacent regression IDs.
6. Update bug status to `Retest Passed` only with fresh evidence.

## Exit Criteria

Full run can be considered successful when:

- Entry checks pass.
- All Critical and High flows are either `PASS` or have approved/understood blockers.
- No `Critical` or `High` open bugs remain for release-critical flows.
- Every `Medium` issue has an owner and workaround/retest decision.
- Every `BLOCKED` item states exactly what is missing.
- Browser console/API failures are classified and not ignored.
- Final report contains evidence index and DEV data created/changed.
- PROD was not touched unless explicitly approved and documented.

## Go / No-Go Guidance

- `Go`: no Critical/High bugs, no unknown blockers, and release-critical flows have the required depth (`UI+API+DB`, plus `PROVIDER/LIVE` where the business promise depends on an external channel/provider).
- `Go with known issues`: only Medium/Low issues remain, documented with workarounds; any missing live/provider layer is explicitly accepted.
- `No-Go`: any Critical/High bug in auth, routing, conversations, message handling, channel setup, Captain runtime UI, data integrity, or cross-account/security behavior.
- `Blocked`: environment/provider/test data prevents confidence; missing blocker must be resolved before release decision.

- `bugs.md`: all bug entries in the bug log template.
- `matrix-results.csv` or `matrix-results.md`: row-by-row result for every test ID.
- `screenshots/`: visual evidence.
- `console/`: console/API error captures where relevant.
- `logs/`: runtime/log/DB evidence snippets where relevant.

Suggested location:

```bash
/root/crafty/onelink/qa-runs/<run-id>/
```

Do not commit run artifacts unless explicitly requested; keep durable methodology in this doc and bug summaries in the chosen tracker/docs only.
