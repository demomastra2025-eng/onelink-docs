# WhatsApp Cloud AI Voice Agent Native Runtime Plan

> **For Hermes:** Use `subagent-driven-development` when executing this plan task-by-task. Keep production read-only until explicit approval. DEV restart/smoke requires explicit approval. Never print secrets.

## Goal

Implement a native, reliable, fast, voice-to-voice AI agent for WhatsApp Cloud API Calls while preserving the existing clean Fonoster/PSTN Voice channel.

The target system must:

- keep WhatsApp Cloud Calls as a native `Channel::Whatsapp` call transport;
- keep Fonoster/PSTN as a separate Voice/Fonoster transport;
- reuse the existing OneLink AI Voice runtime instead of creating a second AI stack;
- reuse Captain as the reasoning/business/tool brain;
- give the voice agent its own realtime humanlike dialogue layer;
- support async/deferred tools without dead air;
- target sub-second perceived response speed;
- preserve recording, transcript, finalization, tools, handoff, cleanup, idempotency, and observability.

## Executive answers

### 1. Will the voice agent answer in 0.5 seconds?

**Target:** yes for the caller-perceived first audible response, but it must be measured at the correct boundary.

There are two different latencies:

1. **First audible acknowledgement / comfort audio**
   - target: `<= 0.5s` after media stream is ready and the runtime has a valid outbound audio path;
   - example: short greeting/acknowledgement/filler such as “Здравствуйте”, “Секунду”, “Да, слушаю”.

2. **Full semantic answer after understanding + tools + Captain reasoning**
   - target: normally `0.7–1.5s` for simple turns;
   - slower if external tools, embeddings, CRM, network, or provider latency are involved.

So the architecture must not promise “every intelligent answer in 0.5s”. The correct production target is:

- `<= 0.5s` to first audible voice response after media readiness;
- `<= 0.7s` to bridge-observed valid first `AUDIO_OUT` / runtime outbound frame where possible;
- `<= 1.5s` for most normal non-tool user turns;
- no dead air during slow tools because the DialogueDirector speaks filler and continues asynchronously.

For WhatsApp Cloud specifically, cold-path setup has more steps than PSTN/Fonoster:

```text
Meta webhook -> Rails -> media-server WebRTC/SDP -> runtime stream -> Node -> Gemini Live
```

Therefore 0.5s is realistic only after the media path is established and optimized with:

- pre-created/fast media-server session;
- parallel context bootstrap and realtime setup;
- immediate short first audio once stream is writable;
- no second recursive route;
- no blocking tools before first speech;
- explicit first-audio telemetry.

### 2. Will tools work asynchronously?

**Yes, they should.** The target design requires two tool modes:

1. **Blocking fast tools**
   - hard timeout: roughly `300–800ms` for trivial CRM/contact/status actions;
   - used only when result is safe and fast enough for realtime speech.

2. **Async deferred tools**
   - return immediately as `pending/request_id`;
   - run in background in Rails/Captain/jobs;
   - DialogueDirector says a short natural phrase instead of silence;
   - when result is ready, it is injected back into the active Gemini Live session if the call is still open;
   - if call is no longer open, result is saved to conversation/note/follow-up.

Slow tools must not block voice-to-voice. This is mandatory for quality.

### 3. How does the voice agent get Captain intelligence but keep its own voice liveliness?

The voice agent should be split into two cooperating layers:

```text
Captain = brain / business reasoning / tools / account knowledge / rules
Voice Agent Runtime = realtime voice behavior / timing / silence / interruption / fillers / turn-taking
```

Captain owns:

- assistant identity;
- system instruction;
- rules/guidelines/guardrails;
- account-scoped tools;
- private/custom tool permissions;
- FAQ/knowledge/CRM/scheduling logic;
- handoff policy.

Voice Agent owns:

- first audible response;
- short spoken style;
- interruption/barge-in behavior;
- silence prompts;
- filler phrases while tools run;
- natural pauses;
- nonverbal micro-cues;
- output cancellation;
- realtime transcript/finalize lifecycle;
- media speed and reliability.

Implementation detail: do **not** create a parallel `Captain::VoiceAgent` model unless a real domain gap appears. The project already has voice settings inside `Captain::Assistant.config['voice_settings']`, and `Telephony::AiVoice::ContextBuilder` already converts Captain + voice settings + tools into runtime context.

### 4. Is this proposal maximally reliable and high-quality?

It is the most reliable architecture for this codebase because it follows the existing OneLink boundaries:

- Rails remains source of truth for accounts, calls, conversations, messages, tools, transcript, recording and finalize.
- WhatsApp Cloud Calls remain native `Channel::Whatsapp` calls.
- Go media-server remains the WebRTC/Meta media layer.
- Node `onelink-ai-voice` remains the realtime AI voice runtime.
- Captain remains the business/assistant/tool brain.
- Fonoster/PSTN and WhatsApp Cloud are separate transports into one shared AI runtime.

The key quality requirement is not only architecture; it is acceptance gating. This plan is not “done” until tests and DEV live smoke prove speed, audio, tools, recording, transcript, finalize and cleanup.

Every call must expose these timestamps:

- `webhook_received_at`

- `routing_decided_at`
- `media_session_create_started_at`
- `media_session_created_at`
- `meta_pre_accept_started_at`
- `meta_accept_completed_at`
- `runtime_stream_ready_at`
- `node_runtime_attached_at`
- `context_ready_at`
- `gemini_setup_complete_at`
- `first_audio_write_at`
- `first_audio_observed_at` when available
- `first_model_audio_at`
- `first_user_audio_at`
- `first_transcript_turn_at`

### Perceived first response target

The first audible response should not wait for all business context and tools if the call already has enough basic context to greet.

Preferred startup order:

```text
1. accept call / establish media
2. create runtime stream
3. start Gemini setup and Rails context bootstrap in parallel
4. when stream writable, send first short audible phrase
5. attach full Captain context/tools as soon as ready
6. continue with semantic dialogue
```

### Avoided latency traps

- No recursive runtime app route.
- No tool call before first speech.
- No FAQ embedding search before greeting.
- No full CRM hydration before the first audible response.
- No waiting for recording setup before streaming audio.
- No browser-agent WebRTC dependency for AI mode.

## Async tool architecture

### Tool catalog fields

Extend tool catalog with voice execution policy:

```json
{
  "name": "faq_lookup",
  "timeout_ms": 6000,
  "realtime_safe": true,
  "voice_execution_mode": "async_deferred",
  "voice_result_delivery": "when_idle",
  "requires_confirmation": false,
  "risk_level": "low"
}
```

Recommended modes:

- `blocking_fast`: contact lookup, simple update, note creation;
- `async_deferred`: FAQ semantic search, CRM search, external HTTP, scheduling availability;
- `confirmation_required`: destructive/high-risk actions;
- `terminal_action`: end call, transfer/handoff.

### Runtime behavior

When a slow tool starts:

```text
Gemini requests tool
  -> Node classifies execution mode
  -> if async_deferred: Rails returns request_id immediately
  -> DialogueDirector says filler phrase
  -> tool runs in background
  -> result arrives by callback/poll/event
  -> Node injects result into active Gemini session if still open
  -> if not open, Rails stores result as note/follow-up metadata
```

### UX rule

The caller should never hear long silence because a tool is slow. The agent should say short natural phrases:

- “Секунду, проверю.”
- “Да, вижу, сейчас уточню.”
- “Почти готово.”
- “Не получилось проверить автоматически, могу соединить со специалистом.”

## WhatsApp Cloud inbound AI call flow

```text
1. Meta sends WhatsApp call webhook.
2. Rails Whatsapp::IncomingCallService creates/updates Call.
3. Rails resolves the Chatwoot Conversation for the caller/inbox.
4. Whatsapp::CallRoutingService decides human_only / ai_only / reject from Conversation.status and channel policy.
5. If Conversation.status == open: keep the call for a human operator; UI rings and the operator answers through the dashboard interface.
6. If Conversation.status == pending: route the call to the AI voice agent; enqueue Whatsapp::AiVoiceAcceptJob.
7. AI job reserves the call idempotently under lock.
8. Rails creates media-server session.
9. Rails pre-accepts/accepts the Meta call.
10. Rails creates or links Telephony::CallSession for AI runtime context.
11. Rails asks media-server for runtime stream.
12. Rails starts Node onelink-ai-voice WhatsApp call attach.
13. Node attaches to runtime stream.
14. Node bootstraps Rails context and Gemini Live.
15. DialogueDirector sends first audio quickly.
16. Gemini + Captain tools drive the call.
17. Terminal event finalizes transcript, recording, call message and cleanup.
```

### Conversation-status routing contract

This is a hard product routing rule for WhatsApp Cloud Calls when AI voice is enabled on the inbox/channel:

- `Conversation.status == open` means a human operator owns the conversation. The WhatsApp call must ring in the operator UI, and the operator takes the call from the dashboard interface. The AI voice agent must not auto-answer this call unless an explicit fallback/overflow policy says so.
- `Conversation.status == pending` means the conversation is waiting for AI/Captain handling. The WhatsApp call should be auto-answered by the AI voice agent, using the Captain assistant attached to the inbox/routing policy.
- If no conversation exists yet, `Whatsapp::IncomingCallService` should create/resolve the conversation according to existing Chatwoot/OneLink rules, then route from the resolved status. The default for AI-enabled inboxes should be explicit in policy, not guessed inside the media-server.
- If the status is neither `open` nor `pending`, routing must fail safe: either `human_ring` or `reject` by policy, but never silently auto-answer by AI without a logged reason.
- This rule is evaluated in Rails only. Go media-server and Node AI runtime receive the already-decided mode and must not re-decide business ownership.

## Human takeover

WhatsApp AI transfer is not PSTN transfer. It is human takeover inside the same media-server session.

Flow:

```text
1. AI calls request_transfer.
2. Rails marks Call as transfer_requested.
3. UI broadcasts transfer event.
4. Human clicks Join/Accept.
5. Media-server creates browser AgentPeer.
6. Active outbound source switches from runtime_ai to agent_peer:<id>.
7. AI becomes listen-only or disconnects.
8. Human talks to caller.
9. Finalize remains idempotent and single-owner.
```

Media-server must enforce:

- only one active outbound source to Meta;
- runtime AI cannot speak over human;
- transfer timeout fallback is explicit.

## Recording and finalize

Recording/finalize is part of PASS, not follow-up.

Required:

- record both caller and AI/human directions when available;
- attach/update exact WhatsApp call message;
- persist transcript turns;
- call finalize once;
- allow late recording metadata enrichment;
- prevent late non-terminal events from reopening terminal calls;
- cleanup Node sessions and Go streams;
- `/health.sessions=0` after terminal.

## Reliability and idempotency

Every boundary must be retry-safe:

- duplicate Meta webhooks;
- duplicate Rails jobs;
- duplicate media-server callbacks;
- duplicate Node finalize attempts;
- caller hangup during accept;
- runtime stream created but Node attach fails;
- Node crashes mid-call;
- Go session terminates first;
- Rails finalization temporarily fails;
- recording arrives late.

Use explicit states:

```text
ringing -> ai_accepting -> in_progress -> transfer_requested -> completed/failed/no_answer
```

Do not do slow network calls inside long DB locks.

## Final architecture verdict

This is the correct OneLink-native direction:

```text
Captain intelligence + Voice Agent realtime behavior + shared AI runtime + separate native transports.
```

It gives the best chance of being fast and reliable because each subsystem keeps its natural responsibility:

- Captain: brain/tools/rules.
- Voice runtime: realtime voice behavior/speed.
- Rails: truth/finalize/tools/messages.
- Go media-server: WhatsApp WebRTC media.
- Fonoster: PSTN transport.
- WhatsApp Cloud: Meta call transport.

The plan is acceptable only if implementation proves speed, async tools, recording/finalize, cleanup and DEV smoke. Architecture alone is not enough.
