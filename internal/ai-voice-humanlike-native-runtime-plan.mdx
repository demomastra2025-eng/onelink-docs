# AI Voice Human-Like Native Runtime Implementation Plan

> **For Hermes:** Use `subagent-driven-development` to implement this plan task-by-task. Keep changes surgical, preserve the dirty tree, and verify each phase with the listed focused checks before moving on.

**Goal:** Make OneLink Captain + AI Voice feel human-like, empathetic, proactive, and fully functional while preserving the current direct Gemini Live voice-to-voice speed target around first audio/first response.

**Architecture:** Keep `gemini-3.1-flash-live-preview` as the realtime voice-to-voice brain. Keep Captain/Rails as the source of business context, guardrails, tool policy, and persistence. Add a native sidecar `DialogueDirector` that controls realtime conversational behavior: silence, fillers, interruptions, async tool wait, deferred tool result injection, and graceful transfer/end-call.

**Tech Stack:** Rails/Chatwoot OneLink Captain, `Telephony::AiVoice` internal APIs, Node.js `services/onelink-ai-voice`, Gemini Live WebSocket, Fonoster managed stream, Vue Captain settings UI, RSpec, Vitest, Node test runner.

---

## Non-Negotiable Product Requirements

1. **No latency regression by design**
   - Keep direct Gemini Live voice-to-voice.
   - Target first audible response/acknowledgement around 0.5 seconds in normal conditions; human-like behavior must not add blocking work before first audio.
   - Do not insert STT -> text LLM -> TTS into the primary path.
   - Do not use extra LLM calls for simple fillers like “Секунду, проверю”.
   - Sidecar-generated fillers must start within roughly 200-300 ms when needed.
   - Do not wait for slow tools, FAQ/search, CRM, scheduling, or post-call persistence before giving the first audible response; use fillers/async handling instead.

2. **No awkward dead air**
   - The caller should never wait silently while tools run, unless silence is intentionally configured.
   - Tool wait, provider setup, delayed model continuation, and user idle must all have deterministic runtime handling.

3. **Agent stays in control of the dialogue**
   - One short question at a time.
   - If the caller is silent, the agent prompts and then gracefully closes or transfers.
   - If the caller interrupts, the agent yields like a human: finishes the current word only, makes a tiny pause, gives a short backchannel acknowledgement such as “ага”, “понял”, “мм”, “аха”, then listens/responds without resuming stale speech.

4. **Captain remains the business brain**
   - Shared Captain settings stay shared: `feature_memory`, `feature_faq`, rules, guardrails, tool access, context access.
   - Voice-specific runtime behavior lives under `assistant.config['voice_settings']`.
   - Do not duplicate Captain memory/FAQ flags into voice settings.

5. **Native, observable, testable implementation**
   - No prompt-only hacks.
   - No hidden mismatch between tool catalog visibility and runtime callability.
   - All new behavior emits safe lifecycle events and is covered by focused Rails/Node/frontend tests.

6. **Operator mode remains a first-class production path**
   - Operator mode is not a fallback, degraded mode, or side effect of the AI runtime rollout.
   - Transfer/operator/recording/topology changes must not be bundled into the human-like AI rollout.
   - Operator changes require a separate contract, joint smoke matrix, rollout gate, and proof of refs, terminal reasons, cleanup, and recording/transcript ownership.

7. **Text Captain behavior remains unchanged by default**
   - Human-like AI Voice changes apply only to `Telephony::AiVoice` sessions and the `services/onelink-ai-voice` sidecar.
   - Normal text-channel Captain runtime must not read or apply `assistant.config['voice_settings']`.
   - Voice-only fields such as `voice_execution_mode`, `voice_result_delivery`, fillers, silence handling, barge-in, and async/deferred delivery are ignored by normal text-channel Captain unless explicitly gated by a separate text feature flag.
   - Shared Captain tools, rules, guardrails, memory, FAQ, and context access may be reused, but existing text behavior must remain backward-compatible.
   - `conversation.status = pending` is not sufficient to start AI Voice; live call activation requires an explicit voice/call session context.

## Current Runtime Summary

### Existing OneLink pieces to preserve

- Rails context builder: `app/services/telephony/ai_voice/context_builder.rb`
  - Emits `context.ai`, `context.captain`, `context.tools`, transfer, recording.
  - Merges routing-policy AI settings with `captain_assistant.config['voice_settings']`.

- Voice tool dispatcher: `app/services/telephony/ai_voice/tool_dispatch_service.rb`
  - Native voice tools: `find_contact`, `create_contact`, `create_note`, `update_conversation`, `request_transfer`, `end_call`.
  - Captain tools are exposed through `captain_assistant.direct_agent_tools`.
  - `faq_lookup` is already voice-optimized with `semantic: false` and a longer timeout.

- Gemini Live client: `services/onelink-ai-voice/src/realtime/gemini-live-client.js`
  - Uses realtime audio input/output.
  - Emits input/output transcripts.
  - Supports provider interruption events.
  - Supports function calling.

- Voice application: `services/onelink-ai-voice/src/app/voice-application.js`
  - Bridges Fonoster media stream to Gemini Live.
  - Sends initial greeting.
  - Handles tool calls, transfer, end call, transcripts, recording, and completion.
  - Has a `postToolWatchdog` that nudges Gemini when a completed tool result does not produce speech.

### Main runtime gap

The system still treats a Gemini tool call mostly as `await tool -> return response`. For slow tools this can create silence. The missing layer is a native sidecar runtime controller that can:

- speak deterministic filler phrases immediately;
- run selected tools in background;
- inject deferred tool results back into Gemini;
- handle idle/silence escalation;
- cancel output cleanly on interruption;
- record observability metrics for latency and dead-air.

### Contract rules

- Preserve explicit `false` and `0`.
- Do not use `value || default` for booleans/numbers.
- Keep `feature_memory` and `feature_faq` as assistant-level shared settings.
- Do not expose provider secrets in context.
- Treat `api_version: v1alpha` as an explicit opt-in for proactive/affective features until verified in production-like DEV.
- Interruption acknowledgements are local deterministic backchannels, not extra LLM calls. They must be short, language-matched, and disabled for urgent/terminal paths where immediate listening is safer.
- Emotionality must be bounded and role-safe: short pauses, backchannels, and warm phrasing are allowed; theatrical sighs, fake heavy breathing, flirting, or over-emotional acting are not production defaults.
- Sparse nonverbal backchannels are part of the out-of-box humanlike default, but capped and suppressible. Sigh/breath cues stay off by default until the exact voice/model renders them naturally in DEV.
- Ambient noise is optional and off by default. If enabled, mix only local prebuffered outbound room tone after model audio is produced; never feed it into Gemini input, VAD, transcript, or tool logic.

### Out-of-box humanlike default profile

Every new Voice Assistant should start with `humanlike_defaults_profile: standard_v1`, not with a bare provider config. The default must already feel usable without manual tuning:

- realtime direct Gemini Live path stays enabled for speed;
- first greeting, closing, transfer phrase, and max two-sentence replies are present;
- interruption handling is on: immediate listening, current-word grace, stale-audio cleanup, micro-pause, and short acknowledgement;
- silence handling is on: first prompt, second guided prompt, and graceful close after repeated silence;
- tool wait handling is on: start phrase, delay phrase, failure fallback, and async/deferred policy;
- naturalness is on: low-intensity warm style, short deterministic pauses, sparse “угу/мм/да” backchannels capped to one per minute;
- risky extras are off: affective/proactive v1alpha flags, sigh/breath acting, and ambient room tone.

The UI may expose “Basic / Advanced” controls, but Basic mode should still preserve this full default profile. A newly created assistant should pass DEV smoke without the operator opening advanced settings.

## Tool Execution Policy

### Tool modes

Add a normalized voice tool policy to the context catalog:

```json
{
  "name": "search_available_slots",
  "source": "captain",
  "enabled": true,
  "realtime_safe": true,
  "timeout_ms": 3000,
  "voice_execution_mode": "async",
  "voice_result_delivery": "when_idle",
  "voice_start_phrase": "Секунду, проверю свободное время.",
  "requires_confirmation": false,
  "risk_level": "low"
}
```

Supported modes:

- `blocking_fast`
  - Expected under ~1000 ms.
  - Gemini can wait for result.
  - Examples: `find_contact`, `get_contact`, `get_conversation`, simple FAQ.

- `async_deferred`
  - Sidecar starts tool in background and immediately gives Gemini/voice a pending acknowledgement.
  - Result is injected when available.
  - Examples: scheduling search, CRM search/update, payments lookup, external HTTP custom tools.

- `terminal_action`
  - Tool causes transfer, hangup, or close.
  - No post-tool continuation unless explicitly configured.
  - Examples: `request_transfer`, `end_call`, `handoff` when mapped to live call transfer.

- `confirmation_required`
  - Sidecar/Captain must collect explicit spoken confirmation before executing.
  - Examples: payment creation/refund, mutating CRM in sensitive contexts, destructive custom HTTP tools.

### First safe default mapping

- `blocking_fast`:
  - `faq_lookup`
  - `find_contact`
  - `create_contact`
  - `get_contact`
  - `get_conversation`
  - `update_conversation`
  - `create_note`
  - `add_private_note`
  - `add_contact_note`

- `async_deferred`:
  - `search_deals`
  - `get_deal`
  - `create_deal`
  - `update_deal`
  - `search_tasks`
  - `create_task`
  - `search_available_slots`
  - `create_appointment`
  - `search_kaspi_pay_payments`
  - custom HTTP tools unless explicitly marked fast

- `terminal_action`:
  - `request_transfer`
  - `end_call`
  - live-call mapped `handoff`

- `confirmation_required`:
  - `create_kaspi_pay_payment`
  - `refund_kaspi_pay_payment`
  - high-risk non-idempotent custom HTTP tools

- Use provider affective/proactive dialog only behind explicit `affective_dialog_enabled` / `api_version: v1alpha` gates after DEV verification.

## Phase 4: Tool Fillers and Tool Wait State

**Objective:** Ensure the caller hears immediate feedback while tools run.

**Files:**

- Modify: `services/onelink-ai-voice/src/tools/tool-executor.js`
- Modify: `services/onelink-ai-voice/src/sessions/voice-session.js`
- Modify: `services/onelink-ai-voice/src/app/voice-application.js`

- Test: `services/onelink-ai-voice/test/tool-executor.test.js`
- Test: `services/onelink-ai-voice/test/dialogue-director.test.js`

**Behavior:**

1. On tool start:
   - emit `tool_started` as today;
   - DialogueDirector sends configured `tool_start_phrase` unless disabled or terminal action.

2. If tool still running after `tool_delay_after_ms`:
   - emit `tool_wait_filler`;
   - send configured delay phrase.

3. On tool success:
   - cancel delay timer;
   - emit `tool_completed`;
   - if blocking tool, return result to Gemini as today;
   - if async tool, inject result when appropriate.

4. On tool failure:
   - cancel delay timer;
   - emit `tool_failed`;
   - say short fallback phrase if Gemini does not respond quickly.

**Safety rules:**

- Never say “готово” before success.
- Never run post-tool continuation for `transfer`, `end_call`, or `hangup`.
- Do not expose raw tool errors or upstream bodies to the caller.

**Async implementation options:**

- Mark compatible function declarations as non-blocking if Gemini Live protocol supports it in the raw WSS format used here.
- Use result scheduling:
  - `WHEN_IDLE` for normal tool results;
  - `INTERRUPT` only for urgent terminal/safety events;
  - `SILENT` for context-only background updates.

1. On async tool call, sidecar immediately sends a tool response like:

```json

  "pending": true,
  "tool_call_id": "...",
  "message": "Проверяю, сообщу результат через несколько секунд."
}
```

2. Run real tool promise in background.

3. When result returns, inject into Gemini with `realtime.sendText`:


## Phase 6: Barge-In Hardening

**Objective:** Interruption must feel instant and must not resurrect stale speech.

**Files:**

- Modify: `services/onelink-ai-voice/src/app/voice-application.js`
- Modify: `services/onelink-ai-voice/src/realtime/gemini-live-client.js`
- Modify: `services/onelink-ai-voice/src/sessions/dialogue-director.js`
- Test: `services/onelink-ai-voice/test/voice-application-streaming.test.js`
- Test: `services/onelink-ai-voice/test/gemini-live-client.test.js`

**Behavior:**

On `serverContent.interrupted` or caller speech while AI output is active:

- cancel active filler/silence timers;
- switch to listening/capture mode immediately on caller speech; caller audio/transcript must continue flowing to Gemini/session state while outbound audio is being drained;
- if `finish_current_word_on_interrupt` is true, allow only a bounded current-word tail up to `interrupt_word_boundary_grace_ms`; this grace affects only outbound playback, never inbound capture;
- clear the rest of `outputPacer` when `clear_audio_on_interrupt` is true so no stale sentence can continue;
- emit `caller_interrupted` and `realtime_interrupted`;
- after the caller's barge-in is confirmed, insert `post_interrupt_micro_pause_ms` and play one local short acknowledgement from `interrupt_ack_phrases` when `interrupt_ack_enabled` is true;
- suppress the acknowledgement when the caller is still speaking continuously, the event is only micro-noise, or the session is entering transfer/end-call/safety handling;
- do not continue old post-tool continuation;
- keep async tool results in state, but deliver them only when the next turn makes sense.

**Human backchannel rule:** The target feel is “the agent was interrupted, politely yielded, and stayed in control” rather than hard robotic cutoff. The allowed sequence is:

```text
AI speaking -> caller starts -> inbound capture continues immediately -> AI finishes current word only on outbound -> ~150-250 ms pause -> “ага/понял/мм/аха” -> answer using the already captured caller turn
```

Do not finish the whole phrase or sentence. Do not say a backchannel over sustained caller speech. Do not let Gemini regenerate the acknowledgement unless provider-native affective dialog is explicitly enabled and verified; default path is sidecar/local audio or a tiny preconfigured phrase.

**Node test cases:**

- interruption with `finish_current_word_on_interrupt: true` keeps only the bounded current-word tail and drops the rest of queued output;
- inbound caller audio/transcript is captured immediately during the outbound current-word tail and is not lost or delayed;
- interruption with the flag disabled clears output immediately;
- confirmed barge-in schedules micro-pause plus one configured acknowledgement phrase;
- sustained caller speech suppresses the acknowledgement so the agent does not talk over the caller;
- terminal actions and safety interrupts suppress acknowledgement and stale continuation.

**Verify:** Interruption clears queued audio after the current-word tail, no stale frames play, and the acknowledgement latency stays inside the configured micro-pause/backchannel budget.

## Phase 7A: Optional Ambient Room Tone

**Objective:** Add optional subtle “office/room tone” without latency regression or speech-recognition quality loss.

**Files:**

- Optional create: `services/onelink-ai-voice/src/audio/ambient-mixer.js`
- Optional assets: `services/onelink-ai-voice/assets/ambient/office-room-tone.pcm`
- Modify: `services/onelink-ai-voice/src/app/voice-application.js`
- Test: `services/onelink-ai-voice/test/ambient-mixer.test.js`

**Behavior:**

- Default `ambient_noise_enabled: false`.
- If enabled, use a preloaded/prebuffered local PCM loop; do not call any model, TTS, network, or file decode path during live speech.
- Mix ambient audio only into outbound frames after Gemini/model audio and local fillers are ready.
- Never include ambient audio in inbound capture, Gemini input, VAD, transcript, recordings used for STT, or interruption detection.
- Keep volume very low, for example around `-42 dBFS`; prefer neutral room tone over recognizable office chatter.
- Duck or mute ambient audio while the caller speaks, during barge-in acknowledgement, and during tool/safety/transfer prompts.
- Make it per-assistant configurable and A/B testable, not a global default.

**Risks:** Too-loud or speech-like noise can harm perceived quality, confuse VAD/barge-in, reduce intelligibility, and feel fake/unprofessional. Recognizable voices in background audio create privacy/compliance risk; use synthetic/non-speech room tone only.

**Acceptance:** First-audio latency is unchanged; no extra network/model call exists on the critical path; interruption detection metrics do not regress; subjective MOS/intelligibility does not drop in DEV smoke calls.

## Risks and Mitigations

### Risk: Affective/proactive Gemini flags break WSS setup

Mitigation:
- Keep disabled by default.
- Gate with `api_version: v1alpha`.
- Add setup-payload tests.
- Smoke in DEV before production.

### Risk: Async tool result interrupts the caller awkwardly

Mitigation:
- Default result delivery: `WHEN_IDLE`.
- Only urgent terminal/safety events use interrupt.
- DialogueDirector stores deferred result if caller is speaking.

### Risk: Fillers become annoying

Mitigation:
- Rate-limit fillers per tool and per turn.
- Do not repeat identical phrase twice in a row.
- Make phrases configurable.

### Risk: Tool mutates data twice

Mitigation:
- Preserve Captain idempotency patterns.
- Use confirmation for risky actions.
- Do not retry mutating tools automatically after Gemini interruption.

### Risk: More settings make UI confusing

Mitigation:
- Hide advanced Gemini flags under advanced section.
- Ship sane defaults.
- Keep MVP UI minimal: silence, interruption, fillers, tone.

### Risk: Operator mode is accidentally degraded by AI runtime changes

Mitigation:
- Treat operator mode as a first-class production path.
- Keep AI human-like rollout separate from operator/transfer/recording/topology changes.
- Do not introduce recursive app handoff or blind direct bridge paths for operator mode.
- Require a separate operator media/lifecycle contract and joint smoke matrix before production.
- Production readiness for operator changes requires confirmed refs, terminal reasons, session cleanup, and recording/transcript ownership.

Keep Gemini Live as the fast voice-to-voice model. Make OneLink feel human by adding a native `DialogueDirector` in the sidecar.
