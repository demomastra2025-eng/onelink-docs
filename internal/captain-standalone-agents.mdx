## Standalone agents — prepared October 11 package

This section describes `feature/independent-agents-20261011`, based on application revision `aeeca102f85ec3a22906b98585f0871107e679e9`. Selected isolated checks of the expanded package passed after focused repeats of corrected cases. The R13 archive `a6393d97a19cc157c347db9a2b9769c32e8cdc9f94bbce919cb6af1d01e74552` covers 497 present files and 13 deletions, including the verified Microsoft classifier and Haiku configuration. Haiku coverage includes 287 selected R12 examples, 25 affected R13 repeats and three effective real-API smoke cases across R14/R15. The R14 tool-loop usage assertion required installing the actual event subscriber, which test boot intentionally skips; R15 rechecked only that case on unchanged application source. Disabled reasoning and streaming had already passed in R14. The evidence combines selected suites at different snapshots, not a single final full-repository run. Deployed DEV acceptance and review of converted-scenario warnings remain required before production promotion. No deployment is implied.

Former scenarios become independent `Captain::Assistant` records. Every agent owns its instructions, model, selected tools, capabilities, safety configuration, follow-ups and knowledge access. The channel selects the entry agent. `handoff_agent_ids` defines directed, account-scoped handoffs to active external agents; an outbound link does not grant a reverse link. The profile and channel assignment use an explicit Save operation. Internal assistants retain their existing independent execution path.

`Captain::AgentGraph` resolves allowed agents. `AgentRunContext` installs the active agent's own model, instructions and tools before each handoff. Shared public conversation content survives, while peer tool payloads and private reasoning are removed from the transferred model history. The parent agent's prompt is not inserted into the specialist's prompt. Durable `captain_agent_session` state belongs to the physical conversation, not the shared contact. The latest authorized agent continues on the next message. Disabling that agent or revoking its route causes a fallback to the entry agent.

The task queue is for multiple independent customer requests. Stable task IDs, assigned agents, states and results survive handoffs. A completed task cannot be reactivated. A customer cancellation can be recorded by the current agent even if the request belongs to another agent. Queues are bounded to 30 requests; graphs to 100 agents. Ordinary calls retain loop limits per task and an overall bound. These are operational limits, not a promise that every model will finish every request in one turn. Unfinished requests remain visible in the session.

The coordination context identifies the currently executing agent and its own task assignments separately from the shared directory and queue. A waiting task is resumed explicitly by its assigned agent after the missing information is available. An agent does not transfer back solely because a peer has a waiting task; when all remaining work needs customer input, the reply explains the results and the missing facts. These instructions do not bypass the server's ownership, authorization or action-replay checks.

For an unambiguously identified appointment belonging to the current customer, an explicit request for an exact new time supplies the requested change; availability is still checked. The tool description does not ask for a redundant confirmation of the same request. Other-patient access retains its scoped token and specific patient/doctor/time/change confirmation. Playground real writes always retain their separate exact-action approval.

Mutating operations are claimed before execution using the task or incoming-request identity and tool. Recorded outcomes are reused for the same actor and arguments. Unknown outcomes and changed arguments cannot resend the action. A peer receives a completion indication rather than private output, and must read the record using its own permissions. Only argument validation that proves no mutation began can release the claim. Tool execution is sequential; an agent or human handoff stops the rest of the batch. Conversation control, message freshness and routing revision fence replies, delayed booking outcomes and follow-ups. Returning from A to B to A does not revive A's previous follow-up chain.

If a request already has a plan and no task is active while unfinished tasks remain, a mutation returns `agent_task_not_active` with `mutation_executed: false`. It does not claim that a provider operation has started. The assigned actor can explicitly resume the existing task after obtaining its missing information; completed tasks and recorded outcomes remain protected against replay. A fully completed plan still returns `mutation_retry_blocked` for an attempt to bypass its task identities.

Before a tool operation or final response, the run fence rechecks the persisted active actor, entry assignment and allowed route without relying on the request query cache. An administrator disabling an actor or removing a route fences an already running request at its next check. An inactive entry agent does not claim new conversations. An already pending conversation returns to staff on its next incoming message; deactivation does not bulk-transition historical conversations. Existing internal-assistant inbox assignments retain their prior eligibility behavior. FAQ generation, memory extraction and automatic completion use the current reachable actor. A delegated actor's follow-up does not require its own inbox assignment: reminder validation, materialization and dispatch verify the entry, actor and routing revision.

Final reply, handoff and automatic-completion persistence acquires locks in the order conversation, shared control owner, inbox assignment, then rechecks ownership. This closes the gap between checking the selected channel agent and writing the result. Model generation does not hold these persistence locks.

Activity reasons remain in scope through the outer transaction commit so the resulting history records the actual completion or handoff reason. A verified, currently bound MedElement create receipt with a reception ID confirms creation even while asynchronous read-back is pending. This operation result does not mark a later move or cancellation as confirmed or repeat the provider command.

### Existing scenarios and knowledge

The two additive migrations create directed handoffs and knowledge grants and convert existing scenarios idempotently. Historical scenario rows and channel associations are preserved. Each converted agent receives its own scenario instructions and explicit tools, plus compatible effective configuration. Original tools remain subject to the new selected-tool control. Migration warnings flag references that need an administrator's review; conversion cannot infer missing instructions that existed only in the parent's prompt.

Knowledge documents and FAQ entries are shared by grants rather than copied. General entries remain available to all permitted agents in the account; selected entries are visible only to their effective owners and grantees. Search, exact matches, derived entries and answer caches use the same access boundary. Editing only FAQ text does not rewrite its permissions. Deleting an owner retains only surviving grants; a restricted child FAQ does not gain the broader access of its document. An entry with no authorized surviving owner or grant is removed according to the existing deletion flow.

### Playground and verification

The playground uses the same agent graph and transfer logic in its temporary Redis session. Caller and synthetic business records remain temporary. Real read and write controls remain separate. Each real mutation requires an exact action approval bound to the entry agent, current actor, route and session generation. A handoff, reset or revoked permission invalidates a stale approval. Runtime results expose `agent_id`, stable `agent_name`, human-readable `agent_display_name` and the task list so the interface can show who answered and what remains.

Playground model overrides apply to the selected entry agent only. A specialist uses its own supported settings; returning to the entry restores the selected reasoning override.

The additive allowlist migration appends Haiku only to the exact previous four-model standard list; absent, empty and administrator-customized values retain their existing meaning. For optional OpenRouter reasoning whose effort list does not include `none`, the interface's off selection compiles to `reasoning: {enabled: false}`. Supported nonzero efforts are sent unchanged; stale contradictory reasoning parameters are removed only when applying the explicit off selection. The raw provider effort list is preserved separately from this interface option.

Provider comparisons use strictly pinned routes in the synthetic benchmark. They do not change production routing preferences or model defaults, and their results do not establish customer delivery or live business-operation success.

### Expanded package: asynchronous outcome classification

An enterprise `ConversationStatusTransition` callback snapshots the allowed reason IDs and labels, locale, and public-message cutoff for a committed Captain completion or handoff. `Captain::OutcomeClassificationJob` claims this event under a lock; inference runs outside the lock. Claims expire after five minutes and stop after three attempts. `Internal::RecoverCaptainOutcomeClassificationsJob` polls only marked pending or processing events older than ten minutes, capped at 100 per run. A partial concurrent index supports this recovery query. Historic unmarked events are not classified retrospectively.

`Captain::OutcomeClassificationService` reads six public messages in the physical conversation, bounded by the captured message ID and transition timestamp. It uses `reorder` to override Message's default chronological order before selecting the latest fragment. A single optional expansion reads at most twenty messages; each content string is capped at 1,000 characters. Classification writes only the transition's reason and metadata. Failed, insufficient-context and pending states are distinct; no business action or external message is retried by this classifier.

The feature `outcome_classification` uses a dedicated `CAPTAIN_OUTCOME_CLASSIFIER_MODEL` administration slot, defaulting to `microsoft/microsoft-decision-1`, independent of the primary assistant and custom-guardrail models. Explicit administrator selections are preserved. `Captain::OutcomeDecisionEngine` maps captured reason IDs to a native choice question; its reserved `NEEDS_MORE_CONTEXT` choice requests the single expansion or records insufficient evidence. It never fabricates prose. `Llm::Runtime.decide` uses the exact supported Microsoft base or dated model through HTTPS `/api/alpha/decisions`, retaining provider/privacy preferences, budget evaluation and sanitized observability. Response caching and chat-generation metadata enrichment are disabled. Native usage/cost is recorded under `llm.decision.complete`; no message text or prompt is persisted in that event. Each request is bounded to 110 seconds with no transport retry, keeping two calls below the 300-second classification lease. Unknown choices and transport failures produce an explicit failed state, not an invented reason. Supported ordinary chat models remain configurable through the existing structured-output path; arbitrary Decisions model IDs are not admitted. Proven FAQ-miss signals are accepted only from the current actor's successful lookup path and an enabled FAQ/handoff capability; provider failures are not FAQ misses.

`Captain::Assistant::MergeLegacyRulesService` is replay-safe. It copies active user rules into the owning agent's description, archives disabled rules in `main_prompt_rules_migration.archived_rules`, and clears legacy rule fields and agent skill bindings. The archive is excluded from public assistant config and runtime prompt construction. Generated platform constraints are not duplicated as user instructions.

### Expanded package: AI business report

`GET /api/v1/accounts/:account_id/reports/ai_agents` uses native ReportPolicy and Reports::DateRange. It accepts optional `assistant_id` belonging to the same account. `Reports::AiAgentEventsQuery` aggregates public outgoing messages authored by Captain::Assistant and actual Captain/system open/resolved status transitions in one SQL snapshot. Message and outcome dates are independent of conversation creation; totals count distinct conversations over the union. `Reports::AiAgentsQuery` fills missing daily rows and supplies totals, series, agents, agent_breakdown, reasons and availability.

Reasons group by actor ID, action type and reason ID; the latest event's captured label is displayed. Unknown or absent classifier state is unclassified. Native author references to an existing foreign-account agent are excluded. Orphan references from previously deleted agents remain only where native identity still exists: Captain::Assistant deletion nullifies message sender identity, so those messages cannot be recovered from display names. No sampling, inferred delivery, false resolution percentages or zero-cost placeholders are used.


### Native provider-response accounting

The prepared R20 observer uses RubyLLM's additive `after_message` callback. Each parsed assistant response, including intermediate tool-loop responses, creates one `llm.chat.complete` usage event with a unique request ID and its outer `parent_request_id`. Tool result messages and restored history are not billed. The callback is installed once per chat and reads the current scoped account, actor and conversation; it does not copy prompts, response text, reasoning or credentials into usage events.

The outer SDK invocation creates `llm.chat.request` with overall status, duration and response count, without another token, cost or generation charge. Nested same-chat wrappers share that invocation. A provider error before a parsed response remains an outer error with unknown usage; it does not fabricate a charged generation. Metadata enrichment keeps the generation's distinct usage identity but correlates its lookup event to the outer request. Enriched provider latency remains available on that usage row and is not averaged again with the outer duration.

An actually observed SDK result carries an internal response marker. Captain completion callbacks emit `llm.chat.runtime_complete` for that result, correlated to the outer request, without generation, token or cost fields; inherited trace usage is stripped. This preserves runtime completion/output metadata without creating an additional usage row. Unmarked legacy responses keep their existing `llm.chat.complete` event.

Usage and simple generation counters count provider responses. Performance budgets use outer requests plus legacy completions as their request/error denominator; the release gate groups child usage by the outer parent and sums each child's cost. This avoids diluting a failed multi-call request across successful intermediate generations. Legacy non-SDK adapters retain their existing completion event. Selected regression and isolated native-style evidence is tracked separately; this contract is not a deployment or full production acceptance claim.
