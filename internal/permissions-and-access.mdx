# Internal Permissions And Access

## Access Layers

```mermaid
flowchart TD
    A[Account] --> B[AccountUser]
    B --> C[Administrator or agent role]
    B --> D[Custom role]
    B --> E[Agent capacity policy]
    A --> F[Team]
    A --> G[Inbox]
    G --> H[InboxMember]
    G --> I[Assignment policy]
```

## Core Access Entities

### `Account`

The workspace boundary. All runtime access logic begins with account scope.

### Super-admin workspace creation

`GET /super_admin/accounts/new` renders an unsaved `Account`. Usage fields must handle that state: `emails_sent_today` returns zero without reading a Redis key before the account is persisted.

`POST /super_admin/accounts` normalizes the form's limit-counter exclusions from the new account's permitted attributes, without resolving `requested_resource`. There is no persisted account ID at this stage. Updates instead merge exclusions into the target account's stored attributes so unrelated settings survive. A supplied top-level ID must not copy another workspace's attributes or hidden feature flags into the new workspace.

Successful creation redirects to the new account's detail page. Focused request coverage includes rendering the form, creation with a blank exclusions field, creation with normalized exclusions/limits/features, loading the resulting detail page, and preservation of unrelated settings during an update.

### `AccountUser`

The per-account identity record. It carries:

- role
- availability
- optional custom role
- optional agent capacity policy

### `InboxMember`

Controls direct user access to an inbox.

### `Team`

Groups users and can be used for ownership, visibility, and reporting.

## Permission Models

### Base Roles

The base role model is simple:

- administrator
- agent

### Custom Roles

Advanced permission tokens come from `custom_roles`. Current permissions include:

- conversation management scopes
- contact management
- CRM deal and task view/manage
- CRM settings view/manage
- report management
- knowledge base management

### Assignment Policies

Assignment policies bind inboxes to routing strategy. They currently define:

- assignment order
- conversation priority strategy
- fairness window
- fairness limits

### Agent Capacity Policies

Capacity policies constrain how much inbox load an agent should carry, optionally per inbox through `inbox_capacity_limits`.

## Access Resolution Pattern

1. Request resolves current account.
2. Current account resolves current account user.
3. Base role and optional custom role permissions are merged.
4. Inbox membership and team context narrow operational visibility.
5. Policy classes apply additional rules by subsystem.

## Why This Matters

This layered model is what allows One Link Cloud to stay one shared product while still supporting:

- simple teams
- admin-controlled visibility
- granular CRM permissions
- knowledge base access
- controlled assignment behavior
