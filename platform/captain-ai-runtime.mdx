# Captain AI Runtime

## Assistant modes and model selection

`Captain::Assistant` is account-scoped and supports `external_agent` and `internal_assistant` usage modes. The model is selected per assistant in its `config.model`; the server validates the value against the model catalog available to the assistant at that time. The API contract does not promise a fixed model list or pricing.

An assistant configuration may include FAQ, memory, citation, web, document-reading, and image-understanding features; handoff and completion behavior; audio transcription; context access; and voice settings. Response guidelines and guardrails are assistant fields. These settings remain separate by assistant and account.

## Tool access

Tool access is stored with each assistant. The external-agent and internal-assistant modes use distinct `agent` and `assistant` tool scopes, respectively. A tool's availability follows the configured scope and its current server definition. This does not create a new account permission role or a broad access-role matrix.

## Follow-ups and outcomes

Follow-up steps are configured in the assistant's existing `config.follow_up_settings` object. Each step uses either a static message or an AI-generated message objective and may include a non-negative delay in seconds. The model validates the configured step array without a fixed maximum number of steps; supported message and objective lengths are still validated.

Scheduled follow-ups use the native Reminder model and transport. Disabling follow-ups cancels that assistant's open follow-up reminders. Follow-up settings are changed through the same assistant update operation as model and tool settings; there are no separate public follow-up routes.

Automation retries may reuse a colliding open reminder only when the originating rule, action, trigger message, content, schedule, and delivery policies match. A manual reminder or a different automation intent remains separate and is not silently merged. Duplicate validation retains its user-facing message and has a distinct machine-readable diagnostic code. Diagnostic logging failures cannot replace the reminder operation's original result or exception.

Outcome reason configuration is also per assistant, under `config.outcome_reason_settings`, and is normalized by the server. It shares the assistant update operation rather than introducing a dedicated endpoint.

## Profile safety settings

The assistant profile accepts `config.safety_settings` with three optional settings:

- `moderation_enabled`: `true`, `false`, or `null` to inherit the workspace default.
- `prompt_injection_action`: `disabled`, `flag`, `block`, or `null` to inherit.
- `sensitive_info_action`: `disabled`, `flag`, `block`, or `null` to inherit.

Explicit profile values override the corresponding workspace preference. Leaving values unset preserves the existing workspace policy. The merged preferences are used by assistant and copilot input/output checks and by instrumented tool argument/result checks, including documentation search. A partial update merges safety fields with the saved object. This configuration uses the existing assistant update endpoint and does not add a separate safety API.

## Playground controls and measurements

The external-agent playground supports request-only `test_model`, `test_temperature`, and `test_thinking_effort` fields on the existing playground endpoint. Model selection is checked against the assistant's account model catalog; temperature must be finite, between 0 and 1, and supported by the selected model. Reasoning effort follows the model's supported capabilities. These controls do not save the live assistant configuration. Internal-assistant playground requests reject these overrides.

Changing assistants resets playground messages and temporary controls and reloads the new assistant metadata. Replies or configuration responses from an earlier assistant request cannot update the current session.

`response_latency_ms` is elapsed server response time measured with a monotonic clock. Provider-reported reasoning token usage is optional. It does not establish a separate duration or speed for hidden reasoning, so the interface does not invent those values.

## Workspace editor controls

Text improvement and label suggestion are workspace controls under Settings → Conversations. The old AI Settings page redirects there. Search, page reading, document reading, and safety settings are configured in the assistant profile. Existing workspace runtime preferences and APIs remain available for compatibility.

Instruction editors use wrapping that preserves entered text and explicit line breaks. Saving a description does not trim its edge whitespace; existing live instruction normalization is unchanged.

## Existing account API

The account-scoped Captain assistant resource supports listing, reading, creating, updating, and deleting assistants. Update model selection, tool access, follow-up settings, and outcome reason settings through `PATCH /api/v1/accounts/{account_id}/captain/assistants/{id}` in the existing `assistant.config` object. The [Application APIs](/api-reference/introduction) list this operation under the `Captain Assistants` tag.

The API remains governed by the existing account authorization. This page records implemented configuration and runtime behavior; it does not imply a new customer portal, automation editor, access-role model, or public activation workflow.
