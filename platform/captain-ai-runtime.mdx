# Captain AI Runtime

## Assistant modes and model selection

`Captain::Assistant` is account-scoped and supports `external_agent` and `internal_assistant` usage modes. The model is selected per assistant in its `config.model`; the server validates the value against the model catalog available to the assistant at that time. The API contract does not promise a fixed model list or pricing.

An assistant configuration may include FAQ, memory, citation, web, document-reading, and image-understanding features; handoff and completion behavior; audio transcription; context access; and voice settings. Response guidelines and guardrails are assistant fields. These settings remain separate by assistant and account.

## Tool access

Tool access is stored with each assistant. The external-agent and internal-assistant modes use distinct `agent` and `assistant` tool scopes, respectively. A tool's availability follows the configured scope and its current server definition. This does not create a new account permission role or a broad access-role matrix.

## Follow-ups and outcomes

Follow-up steps are configured in the assistant's existing `config.follow_up_settings` object. Each step uses either a static message or an AI-generated message objective and may include a non-negative delay in seconds. The model validates the configured step array without a fixed maximum number of steps; supported message and objective lengths are still validated.

Scheduled follow-ups use the native Reminder model and transport. Disabling follow-ups cancels that assistant's open follow-up reminders. Follow-up settings are changed through the same assistant update operation as model and tool settings; there are no separate public follow-up routes.

Automation retries may reuse a colliding open reminder only when the originating rule, action, trigger message, content, schedule, and delivery policies match. A manual reminder or a different automation intent remains separate and is not silently merged. Duplicate validation retains its user-facing message and has a distinct machine-readable diagnostic code. Diagnostic logging failures cannot replace the reminder operation's original result or exception.

Outcome reason configuration is also per assistant, under `config.outcome_reason_settings`, and is normalized by the server. It shares the assistant update operation rather than introducing a dedicated endpoint.

## Profile safety settings

The assistant profile accepts `config.safety_settings` with three optional settings:

- `moderation_enabled`: `true`, `false`, or `null` to inherit the workspace default.
- `prompt_injection_action`: `disabled`, `flag`, `block`, or `null` to inherit.
- `sensitive_info_action`: `disabled`, `flag`, `block`, or `null` to inherit.

Explicit profile values override the corresponding workspace preference. Leaving values unset preserves the existing workspace policy. The merged preferences are used by assistant and copilot input/output checks and by instrumented tool argument/result checks, including documentation search. A partial update merges safety fields with the saved object. This configuration uses the existing assistant update endpoint and does not add a separate safety API.

## Playground controls and measurements

The external-agent playground supports request-only `test_model`, `test_temperature`, and `test_thinking_effort` fields on the existing playground endpoint. Model selection is checked against the assistant's account model catalog; temperature must be finite, between 0 and 1, and supported by the selected model. Reasoning effort follows the model's supported capabilities. These controls do not save the live assistant configuration. Internal-assistant playground requests reject these overrides.

Changing accounts or assistants resets playground messages and temporary controls and reloads the new assistant metadata. Replies or configuration responses from an earlier account, assistant, or reset cannot update the current session.

The prepared playground correction returns account-scoped `playground_model` metadata when reading an external assistant. This identifies the assistant's resolved saved model even when it is absent from the curated selection list; it does not add that model to other assistants' selectable models. Supported reasoning efforts come from the model catalog. The `none` test option is offered only when the provider metadata permits disabling reasoning, and an explicit playground override is carried to the native provider request. A zero temperature remains zero. Existing workspace reasoning preferences and the live assistant configuration are unchanged. Deployment and verification of this correction are tracked separately.

`response_latency_ms` is elapsed server response time measured with a monotonic clock. Provider-reported reasoning token usage is optional. It does not establish a separate duration or speed for hidden reasoning, so the interface does not invent those values.

## Prepared synthetic workspace correction

The next October 10 correction is being implemented and verified separately from the deployed revision. It replaces the Trial/Live selector with one playground. Caller, contact, patient and added scenario records always remain synthetic. A server-owned Redis JSON session expires after 24 hours; it does not insert those records into the clinic's contact, conversation, appointment or deal tables. Synthetic record IDs belong to that session and cannot be promoted into real IDs.

“Чтение реальных данных” and “Изменение реальных данных” are separate switches. Both start disabled. Changes require reads; disabling reads disables changes and invalidates pending confirmations. The synthetic caller remains synthetic when real access is enabled. Account membership, the current agent's selected tools and the operator's record permissions still apply.

Each real change has its own server-generated preview and explicit confirmation. Approval is bound to the account, operator, assistant, session, tool, exact arguments and record snapshot. Changed targets, expired previews, reset sessions and disabled permissions require a new preview. Replaying a confirmation cannot repeat an executing or completed action. A tool response that requests confirmation is not a completed business operation.

Synthetic tools retain the production schemas and use shared domain validation where available. For example, scheduling snapshots adapt the production availability engine, and custom-field definitions use the production field catalog without copying customer values. Unsupported operations return an explicit error rather than falling through to the database or an external service. The support matrix and its parity tests must be checked at the prepared revision before deployment.

External message delivery, opaque custom HTTP tools, MCP connections and skill scripts remain blocked in this playground. Signed run policies also govern delayed provider commands. A revoked approval cannot authorize a new MedElement write; already sent legacy commands retain their reconciliation path without a second send. Normal production agent operations retain their own policy.

External-agent requests use server-owned history. `playground_action: session` reads or edits a scenario, `reset` starts a fresh session, `permissions` controls real access, and `confirm` approves the exact pending action. A normal request sends `message_content` with the session ID. Temporary model overrides remain per request. Profile and playground controls are grouped under the settings gear; parameters without confirmed model support are neither shown nor sent.

## Prepared compact related-record summaries

`appointment.summary` and `deal.summary` share a versioned envelope containing record scope, counts, groups, selection rules, sorting and `shown`/`total` values. This is a bounded summary, not a complete record history or an automatically selected main deal.

Deal summaries contain at most eight active and four closed or archived rows. Active deals sort by `updated_at` descending, then ID descending. History sorts by its recorded close/archive event descending, with an explicit `created_at` fallback when that event is unavailable. Unused group capacity is not transferred to another group: five active and 295 historical deals show nine of 300.

Appointment summaries contain at most six ongoing or upcoming, three past and three cancelled rows. Ongoing visits precede future visits, which sort by start ascending. Past visits sort by end descending. Cancelled visits sort by their planned start descending, not an inferred cancellation time. Each group and the whole summary report how many rows were shown out of the matching total.

Each row contains its own ID and identifying details. A scoped tool can fetch that exact full record, or page through a filtered list. The agent must select a row explicitly before changing a deal; an ordinary conversation does not imply a current deal. Old scalar deal fields remain available in an explicit validated CRM event context, while obsolete references are hidden from new field insertion and remain compatible with existing templates.

The customer agent's unusable `get_appointment_provider_status` tool is removed by the prepared correction. Internal provider reconciliation and the internal assistant's status lookup remain separate and are preserved.

## Prepared booking replies and FAQ correction

An occupied booking time produces one public explanation that the booking or move could not be completed, together with the staff handoff. A newer request or human takeover still prevents an obsolete reply. Incoming requests in separate conversations of the same contact do not cancel one another's replies; shared history and human takeover remain governed by their existing policies.

Scheduling tools distinguish invalid dates, invalid ranges, unknown services, unavailable provider checks and internal failures. Input errors give the agent a concrete correction; an unavailable check must not be described as free time or trigger a repeat of an uncertain provider write.

FAQ retrieval retains its existing strong semantic threshold. A short or misspelled question below that threshold can be accepted only when the leading result's question independently matches its meaningful terms and competing matches are sufficiently distinct. An ambiguous or different-intent question remains unmatched. English word-form corroboration is limited to plural suffixes; it does not equate a changed topic such as account and accounting. This additional decision does not turn its lower semantic score into a strong match and is not reused through the semantic answer cache. Positive and negative corpus checks are required before deployment.

## Booking for a specifically identified patient

The existing `create_appointment` tool accepts an optional `patient` object with first and last names, IIN, birth date, gender and phone. It resolves or creates a separate clinical card while preserving the communication contact and conversation. An existing recorded IIN cannot be adopted from arbitrary public contact data, and booking does not rewrite an existing patient's identity or phone.

The existing appointment search can locate a specific other patient's task by exact IIN, or by exact full name plus doctor and appointment date. It returns minimal appointment information and an opaque task token. Update and cancellation require confirmation of the particular patient and change. The token binds the account, assistant, original conversation and exact appointment snapshot; mutation rechecks it under the appointment lock. This permits the requested task without granting access to that patient's other conversations or full appointment history.

Booking and changes distinguish a confirmed provider result, a pending operation and a local-only cancellation. An AI must not describe a queued MedElement move or removal as completed. Manual start time and duration use the same full-free-interval check as staff booking.

Availability of the prepared implementation depends on the deployed revision and its completed verification.

## Workspace editor controls

Text improvement and label suggestion are workspace controls under Settings → Conversations. The old AI Settings page redirects there. Search, page reading, document reading, and safety settings are configured in the assistant profile. Existing workspace runtime preferences and APIs remain available for compatibility.

Instruction editors use wrapping that preserves entered text and explicit line breaks. Saving a description does not trim its edge whitespace; existing live instruction normalization is unchanged.

## Existing account API

The account-scoped Captain assistant resource supports listing, reading, creating, updating, and deleting assistants. Update model selection, tool access, follow-up settings, and outcome reason settings through `PATCH /api/v1/accounts/{account_id}/captain/assistants/{id}` in the existing `assistant.config` object. The [Application APIs](/api-reference/introduction) list this operation under the `Captain Assistants` tag.

The API remains governed by the existing account authorization. This page records implemented configuration and runtime behavior; it does not imply a new customer portal, automation editor, access-role model, or public activation workflow.
