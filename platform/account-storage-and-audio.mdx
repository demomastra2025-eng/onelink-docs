# Account Storage And Recording Lifecycle

## Storage accounting

Storage is measured per account. The physical usage summary deduplicates Active Storage blobs within that tenant and includes locally stored call recordings. Provider-hosted recording URLs and stale recording size metadata do not count as local disk usage. Shared Active Storage files are counted once for the account that owns them.

The overview serves the last background measurement. A first calculation is shown as pending, rather than as a completed zero-byte measurement. Refresh distinguishes newly queued work, existing work, and enqueue failure. The last measured figures remain visible while a refresh is pending; a failed refresh does not replace them with zero.

Routine recording accounting uses current ingestion/compression sizes and saved physical measurements. A shared daily reconciliation measures tenant files, including legacy files, retained originals, trash, and files not linked to a call session. Hard links are counted once. File changes made outside OneLink may remain reflected in the previous measurement until that reconciliation; `recordings_reconciled_at` identifies its audit time. Overview, quota, large-file listing, trash listing, and ordinary administrator usage reads do not traverse recording directories.

Large-recording filters apply to the account's current call sessions before sorting and limiting, so a recording can be found even when it is outside the account's largest 200 files. Playback links use the current recording reference. Missing legacy size metadata is shown as an incomplete calculation; query failures are not reported as an empty list. The page refreshes pending results and reloads visible lists after cleanup and restore actions.

The displayed account allowance is informational. The current `AccountLimits::StorageUsageService#within_limit?` returns true, so uploads, imports, messages, and attachments remain available above the displayed allowance. The summary reports usage; it does not enforce an intake, outbound-message, or upload stop.

Account administrators can use the account storage API to show or refresh the usage breakdown, list large files, preview cleanup, move the exact previewed set to trash, inspect trash, restore items, or permanently purge trash. These are account-scoped operations. The Super Admin interface and its internal routes are outside the public REST contract.

## Cleanup and trash

Cleanup starts with a read-only preview. It defaults to files older than six months and returns counts, byte totals, samples, and a short-lived confirmation token bound to the account, acting administrator, and exact manifest. Moving files to trash requires confirmation and that matching token; a stale or changed preview must be generated again.

Unlike the overview and large-file list, the signed cleanup preview still resolves and checks the selected physical files. This preserves the exact confirmation manifest used by the existing cleanup workflow.

Trash is retained for 30 days. Trashed attachments and recordings still count toward physical usage until they are permanently purged. Administrators may restore one item or restore the full trash. Permanent purge requires explicit confirmation and either names one item or, when no item is named, empties the trash. The daily housekeeping job purges expired trash; there is no active-file age job that removes files merely because they are old.

Cleanup and restore do not delete the related conversation or task record. Recording transcripts and call metadata remain available when an audio file is moved or compressed.

## Call recording compression

The recording compressor converts supported local WAV recordings to stereo MP3 at 64 kbps. It probes the source and output durations, fully decodes the output with FFmpeg, and rejects output whose duration differs by more than one second. It publishes the new file before switching the database references under the recording lock. A failed validation or reference update leaves the original as the playable recording.

After a successful switch, the original WAV remains available for 30 days. Both copies continue to count as physical storage during that recovery period; no space is released until the retained original is purged. The configured housekeeping job removes expired retained originals. Docker installs FFmpeg and FFprobe, which the service uses for encoding, decoding, and duration validation.

Historical conversion is an account-scoped operator task and defaults to a dry run. It requires an account ID, processes no more than 50 recordings per batch, and can resume after the last call-session ID. An operator must explicitly set `dry_run=false` to perform conversion. The provided task selects WAV/WAVE recordings; completed-call jobs also process the service's supported PCM references.

## Relevant implementation and API paths

- Storage accounting: `app/services/account_limits/storage_usage_service.rb` and `app/models/account.rb`.
- Cleanup: `app/services/storage/trash_service.rb`, `app/jobs/storage/purge_expired_trash_job.rb`, and the account-scoped `storage` API.
- Audio: `app/services/telephony/recording_compression_service.rb`, `app/jobs/telephony/compress_recordings_job.rb`, and `app/jobs/telephony/purge_retained_recordings_job.rb`.
- Scheduled housekeeping is configured in `config/schedule.yml`.

The public account storage operations appear in [Application APIs](/api-reference/introduction) under the `Account Storage` tag. The page describes current behavior; it does not define quota pricing or account-specific plan terms.
