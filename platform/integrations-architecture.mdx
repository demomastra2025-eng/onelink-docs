# Integrations Architecture

## Status

- document type: current model plus extension guidance
- source of truth for the implemented model: code
- use this page as a rule for deciding between integration surfaces, not as proof that every domain-specific integration already exists

In Onelink, integrations should be treated as a shared platform capability with domain-aware configuration, not as a separate architecture per vertical.

## The Native Model In This Repo

There are two main integration concepts already present in the codebase.

### `Integrations::App`

`Integrations::App` is the app catalog and capability descriptor.

It defines things like:

- integration id
- display metadata
- connection action URL
- fields
- feature flag requirements
- hook type
- settings schema

Use it as the catalog entry or integration definition layer.

### `Integrations::Hook`

`Integrations::Hook` is the installed integration instance.

It belongs to an `Account` and can optionally belong to an `Inbox`.

Use it as the connected integration layer:

- account-level connection
- inbox-level connection
- stored settings
- access token / reference id
- post-install setup behavior

## Architectural Fit

```mermaid
flowchart TD
    A[Shared Platform] --> B[Integrations::App catalog]
    A --> C[Integrations::Hook installed instances]
    A --> D[Captain::CustomTool action tools]

    B --> E[Generic tenants]
    B --> F[Healthcare tenants]
    B --> G[Construction tenants]

    C --> E
    C --> F
    C --> G

    D --> E
    D --> F
    D --> G
```

## How This Fits With Domain Zones

Integrations belong to the shared platform layer because the mechanics are common:

- connection lifecycle
- auth
- settings validation
- account/inbox scoping
- UI installation flow

The domain-specific part should usually be:

- which integrations are relevant
- which settings are required
- what workflows consume the integration
- which Captain tools or automations use the external system

So the rule is:

- integration framework = shared
- integration usage = domain-aware

## Practical Distinction

Use `Integrations::App` and `Integrations::Hook` when:

- you are connecting an external system to the product
- the system has install/auth/config lifecycle
- the connection belongs to account or inbox
- the integration should appear in the integrations UI

Use `Captain::CustomTool` when:

- the external action is primarily an AI tool callable by Captain
- you need an account-scoped HTTP action surface
- the tool is part of assistant behavior rather than a full product integration lifecycle

## Domain Examples

### Generic

- Slack
- Linear
- Shopify
- Notion
- generic CRM/ERP integrations

### Healthcare

- medical scheduling systems
- insurer lookup systems
- clinic knowledge systems
- domain-safe Captain tools for lookup or triage support

### Construction

- project calculators
- estimate systems
- ERP or procurement systems
- domain-safe Captain tools for project or estimate lookup

## Design Rule

Do not build a separate integration architecture for healthcare or construction.

Instead:

- reuse the shared integration framework
- add domain-specific manifests, workflows, settings presets, and tool usage
- introduce a new shared integration only when more than one domain needs the same mechanics

## Recommended Decision Pattern

1. If the need is a standard external app connection, start with `Integrations::App` + `Integrations::Hook`.
2. If the need is an AI-callable external action, start with `Captain::CustomTool`.
3. If the need is domain-specific but the mechanics are still generic, keep the infrastructure shared and move only the configuration into the domain zone.
4. Only add a new domain-specific integration model if the shared installation and hook model is no longer correct.

## Calendar Display And MedElement Availability

The calendar grid currently displays OneLink work rules, breaks, holidays, overrides, time off, and appointments. Importing or refreshing MedElement schedule data does not automatically rewrite those local rules. The displayed working hours therefore are not a promise that every visible slot is bookable in MedElement.

For a specialist linked to MedElement, slot search additionally checks the provider's working windows and cabinet occupancy. Explicit local work rules and day overrides restrict those provider windows; local breaks, blocks, and occupied appointments also restrict the result. A seeded default work template can be replaced by the provider's working windows when no explicit local override exists. An unavailable provider check must not be presented as confirmed free time.

Provider schedule summaries in resource settings are a separate view with a check timestamp and a confirmation state. They do not make the calendar grid a live mirror of the MedElement schedule. This distinction follows `Scheduling::CalendarViewService`, `Scheduling::ResourceScheduleService`, `Scheduling::AvailableSlotSearchService`, `Scheduling::AvailabilityService`, and `Integrations::MedElement::ResourceAvailabilityService`.

The prepared October 10 implementation permits entering start, end and whole-minute duration directly in the calendar and conversation sidebar. The entire interval must be free and covered by the applicable schedule; extending an appointment does not reserve only its original slot. Duration is 5–1440 minutes. For MedElement resources, a missing or unverifiable provider response is not treated as free time. The background cache window is not a fixed booking-date prohibition: confirmed dates outside it are read on demand, while normal cached dates use confirmed stored schedule evidence. Availability reads occur before the mutation transaction; clinical patient selection and final local conflict checks occur under transaction locks.

## MedElement Sync Recovery

Saving a local appointment or approving a provider command does not by itself establish that MedElement created a reception. The prepared October 10 correction treats a successful MedElement creation response containing a valid reception ID as success. Delayed visibility in MedElement's read API is checked separately inside the integration; it does not turn that receipt into a refusal or authorize another creation. If the patient has no verified provider identity, the operation can pause for explicit patient selection, patient creation confirmation, or phone refresh confirmation before any reception write. A single search candidate still requires selection when strong identity is missing. The interface must distinguish this pending state from provider success and preserve the local appointment for continuation.

### Shared-phone patient selection

The prepared patient-selection implementation keeps the communicating contact and the appointment patient separate. A shared family phone can carry one conversation while each patient retains their own card and medical identity. An existing communicating contact can itself be the verified patient; this does not require a duplicate card or moving its medical profile to another contact. Matching a phone alone does not establish patient identity.

Authorized staff can list the patients connected to a conversation contact and explicitly create a local patient card. Listing or switching patients does not create a card or a provider reception. Creating a card requires a stable request key; repeating that same request returns its existing result. Appointment creation and filtering accept the selected patient separately from the contact used to communicate.

When staff explicitly select a MedElement candidate for an operation that has not started a provider write, continuation verifies the original booking, confirmation, provider instance and patient identity. Any admitted change retains the original snapshot and confirmation, creates a fresh confirmation for the new patient snapshot, and updates the command result binding consistently. Operations with a provider write or incompatible identities retain their safeguards. Reusing a verified communicating contact does not save or rename that contact, change its phones, or rewrite older appointments and receipts.

The selector projects server-recorded clinical names, identity and birth information for booking. The communicating contact's chat label remains independent. Details supplied by MedElement are shown as provider information; generic contact editing must not write that projected profile over the chat contact.

These paragraphs describe the prepared implementation. Availability depends on the deployed application revision and its completed verification; they do not authorize automatic patient selection or retrying a real reception creation.

MedElement sync recovery distinguishes queued work from an abandoned execution. Cron requests can merge additional phases without advancing the worker activity timestamp. Worker heartbeats and execution identity are kept separately; private worker identity is excluded from public sync summaries.

A known execution becomes eligible for recovery after ten minutes without worker activity only when its process is absent, no matching job is in a queue, schedule, retry set, or active work, and the account mutex can be acquired. Runs with incomplete legacy identity retain the forty-five-minute threshold. A surviving thirty-minute mutex lease can delay recovery. A live owner process or present job prevents this recovery, even when the run is old.

Recovery rechecks state while holding the hook/run locks, renews its own mutex token, and preserves remaining and merged phases for continuation. Token-checked release does not remove another worker's mutex. This mechanism does not activate unavailable specialists or change appointments in MedElement.

Scheduling appointments, services, and resource slot durations accept 5 through 1,440 minutes. A valid long appointment imported from MedElement uses the same range as a manually created appointment. An end time at or before the start remains invalid; OneLink does not invent a replacement time. The calendar's five-minute search step is independent of the permitted appointment duration.

An existing invalid-reception conflict remains open when detail retrieval is deferred, omitted, or yields a stale snapshot. A successful reception phase does not by itself establish that each deferred reception was imported. Only a later processed result or confirmed absence allows that reception's earlier conflict to resolve. Deferred receptions retain their external references during absence reconciliation, so deferral does not delete their appointments.

## Prepared confirmed-calendar follow-up

Cancellation only in OneLink leaves an active MedElement reception occupying its interval. Time becomes available only after confirmed provider removal or an authoritative synchronization result establishing that it has been freed. Enabling removal in the integration settings does not itself free a previously occupied interval. Provider confirmation identifies the particular creation, move or cancellation and where it occurred; a prior successful move cannot confirm a later local cancellation.

A newly acknowledged creation is protected from absence reconciliation until its exact reception and patient have been observed by the provider read path or native import. Empty snapshots and exhausted read attempts alone do not cancel that appointment. Explicit provider removal remains authoritative. This protection is bound to the current creation receipt; it does not change absence handling for older read-confirmed appointments.

The October 10 bulk-calendar follow-up is prepared separately from the deployed release. The display uses saved confirmed provider schedules instead of sequential live MedElement schedule and reception requests for each specialist. A missing or expired confirmation produces an unknown schedule; it does not make the day free. Existing appointment rows remain visible. Single-resource availability and booking retain their live verification path, and a provider command must still confirm a booking result.

The existing availability endpoint accepts `confirmed_only=true` for a bounded search over saved schedules. This disables live provider requests for that search. Partial or unknown ranges can expose verified windows without claiming that unconfirmed days are empty. The booking panel keeps the doctor, service, cabinet and full duration filters when looking ahead.

## WhatsApp Cloud Usage Reporting

The prepared monthly usage response adds `category_breakdown` alongside the existing totals and estimate. It returns rows in this fixed order: `service`, `utility`, `marketing`, `authentication`, `authentication-international`, `referral_conversion`, and `unknown`. Every deduplicated delivery contributes to one row; each row reports `delivered_count`, `chargeable_count`, `free_count`, and `unknown_billable_count`. The rows sum to the overall delivered count. Meta's actual `pricing.billable` value is authoritative: `true` is chargeable, `false` is free, and a missing or invalid value is unknown. Missing or unrecognized categories map to `unknown`.

Reporting combines the delivery ledger with eligible message history and deduplicates by canonical business phone number and provider message ID. A ledger delivery timestamp determines its UTC reporting month. When a legacy outgoing or template message created during the current UTC month is already confirmed as delivered or read but has no exact delivery timestamp, it may be counted for that month with coverage marked incomplete. Never infer or store an exact delivery time from a message's creation or update time. In coexistence, messages sent from the WhatsApp Business app and supported linked WhatsApp Web remain free and are excluded from OneLink Cloud API counts and estimates.

The reporting window is the UTC calendar month. The observed free-service count includes only deliveries with `pricing.category=service`, `pricing.type=free_customer_service`, and `pricing.billable=false`; the allowance is 1,000 per connected business phone. `free_entry_point` is not included. Meta's allowance period follows the WhatsApp Business Account timezone, so the UTC observation cannot establish the exact remaining Meta quota. The estimate follows Meta's billability flag and does not subtract the free-service allowance a second time.

The estimate uses the versioned Meta USD base-rate catalog effective 1 October 2026, selected by recipient market and category, and converts billable deliveries with an immutable NBK USD/KZT snapshot requested for the first day of the same UTC month. Template deliveries use their Meta category rates; there is no flat KZT 8 template rate. The estimate excludes volume discounts, taxes, and provider markup, and is not an invoice total. Missing rate, recipient market, category, or exchange-rate data leaves the affected amount unavailable or incomplete rather than zero; do not extrapolate rates beyond their effective period.

This describes the prepared implementation; availability is determined by the deployed application revision.

The usage banner dismissal is browser- and account-scoped, expires at the next UTC day boundary, and ignores legacy monthly dismissals.
