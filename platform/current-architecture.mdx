# Current Architecture

## Status

- document type: current state
- source of truth: code in `app/`, `enterprise/`, `config/`, and `db/`
- use this page before reading target architecture pages

## Current Product Shape

The current codebase is primarily:

- an account-scoped omnichannel support platform
- a Rails monolith with a Vue 3/Vite frontend split into dashboard, widget, portal, survey, and SDK entrypoints
- a shared communication core around `Account`, `Inbox`, `ContactInbox`, `Conversation`, and `Message`
- an inherited `enterprise/` technical split under `enterprise/`; in Onelink this is an implementation layer, not a separate product/paywall boundary, because enterprise capabilities are currently opened for the project
- a first-class, account-scoped CRM subsystem with deals, pipelines, stages, task catalogs, field definitions, events, and comments, built around shared records such as `Contact`, `Company`, `Note`, and `Label`
- account-scoped storage accounting and administrator cleanup workflows, with local call recording compression and retention
- a native shared scheduling and kassa capability under `app/models/scheduling`, `app/services/scheduling`, and `app/javascript/dashboard/routes/dashboard/scheduling`
- an event-driven application with listeners, jobs, hooks, reporting, automations, and AI/Captain features around the conversation core

## Frontend Runtime

The implemented frontend shape today is:

- `Vue 3 + Vite` attached to the Rails monolith rather than a separate Nuxt-style app shell
- multiple entrypoints such as dashboard, widget, portal, survey, and SDK
- incremental frontend modernization with both `Vuex` and `Pinia` active in the dashboard
- a newer shared UI layer in `app/javascript/dashboard/components-next/`
- older shared UI layers and route-local composition still present across the dashboard
- `VueUse` already active as the shared frontend utility layer through `@vueuse/core` and `@vueuse/components`
- a native scheduling dashboard module using `Pinia` stores, `dashboard/api/scheduling/*`, and `components-next/Scheduling/*`
- Tailwind preferred for new work, while SCSS and scoped styles remain in older surfaces
- `Histoire` and `Vitest` already available for component development and verification

### AI / Captain

Core records:

- `Captain::Assistant`
- `Captain::Document`
- `Captain::CustomTool`
- `Captain::Scenario`
- `CopilotThread`
- `CopilotMessage`

Key behavior:

- Captain provides assistant, copilot, document, tool, and scenario flows around the conversation core.
- Assistant configuration is per account and per assistant. The selected model is stored in the assistant config and validated against the supported assistant model catalog.
- The existing `external_agent` and `internal_assistant` modes use separate `agent` and `assistant` tool-access scopes. The mode is configuration on the current assistant model, not a new account role.
- Follow-up configuration supports a list of static-message or AI-objective steps and uses the native Reminder model for delivery. Outcome reason settings use the same assistant config.
- Model, tool, follow-up, and outcome reason changes share the existing account-scoped assistant update API. See [Captain AI Runtime](/platform/captain-ai-runtime) for the implemented fields and limits.

This describes current code and API behavior; it does not declare a separate internal-assistant activation workflow.

The assistant form keeps the existing `external_agent` and `internal_assistant` usage modes and groups controls for customer context, tools, and voice. `AssistantBasicSettingsForm.vue` and `AssistantUsageModeSelector.vue` present these existing settings; `toolAccessDefaults.js` supplies defaults for the supported usage modes. The headings are display groupings backed by `Captain::Assistant` configuration:

- Customer context: FAQ and memory settings use `feature_faq` and `feature_memory`.
- Tools: citations and web access use `feature_citation` and `feature_web`; `tool_access` keeps separate `agent` and `assistant` scopes for notes, web search and page reading, FAQ lookup, and human handoff.
- Voice: external-agent audio transcription uses `use_audio_transcriptions` when that capability is available.

Internal-assistant mode uses its existing `assistant` tool-access scope. The form hides external-agent-only customer-context, web, FAQ-lookup, handoff, and voice controls in that mode. These controls do not add Captain models or permission roles.

### CRM

Implemented today:

- `Contact`
- `Company`
- `Note`
- `Label`
- `CustomAttributeDefinition`

- `Crm::Deal`, `Crm::Pipeline`, and `Crm::Stage`
- `Crm::Task` and `Crm::TaskStatus`
- `Crm::FieldDefinition`, `Crm::Event`, and `Crm::Comment`

The CRM is a first-class, account-scoped subsystem, not only a layer adjacent to contacts and companies. The dashboard provides deal and task workspaces. Tasks have list, calendar, and due-date planning-board presentations. The board uses rolling local-time boundaries: overdue, today, tomorrow, through the start of the day eight days after today, through the same calendar date next month (clamped to that month's last day), later, and unscheduled. It hides completed and archived tasks. The list and calendar presentations remain available.

Pipeline settings support ordered stages, default-stage configuration, transition and closing reasons, and atomic stage-list updates. The current CRM reports screen is under Settings → Reports, with Activity as one section of the deal reporting page. Its component is `CRMActivityReports.vue`; it reads the report rows from `data.payload.rows`. See [CRM Architecture](/platform/crm-architecture) for report semantics, legacy data behavior, and the current API contract.

## Primary Runtime Flows

### Inbound Message Flow

```mermaid
flowchart TD
    A[Webhook, email, widget, API] --> B[Find or create ContactInbox]
    B --> C[Find or create Conversation]
    C --> D[Build Message]
    D --> E[Dispatch events and jobs]
```

### Access Resolution Flow

```mermaid
flowchart TD
    A[Request] --> B[Authenticate user or access token]
    B --> C[Resolve Current.account]
    C --> D[Resolve Current.account_user]
    D --> E[Apply policy and scoped queries]
```

### Event Fan-Out Flow

```mermaid
flowchart TD
    A[Model callback or service action] --> B[Dispatcher]
    B --> C[Realtime listeners]
    B --> D[Automation listeners]
    B --> E[Notification and reporting listeners]
    B --> F[Hook and webhook jobs]
```

## Not Implemented Yet

These appear in planning docs but should not be treated as existing runtime layers unless code is added:

- dedicated `generic`, `healthcare`, and `construction` runtime zones
- a normalized cross-entity `Activity` model that replaces or unifies the existing CRM task, event, comment, and scheduling records
- a fully separated domain architecture beyond the current shared code plus inherited `enterprise/` technical split
